# Xen backend на Rust

## Цель

Разработать backend для управления гипервизором Xen на Rust. Использовать libvirt не планируется; предпочтение отдано нативному Xen toolstack.

## Выбранное направление

Основной интерфейс — **`libxl`** из репозитория [xen-project/xen](https://github.com/xen-project/xen). `xl` — CLI над этим toolstack’ом и полезный пример работы с ним; для backend’а предпочтительно вызывать API `libxl`, а не разбирать вывод команд.

Для Rust-интеграции потребуется FFI-слой и безопасная обёртка над ним. В ходе предварительного поиска зрелого Rust control plane для Xen не обнаружено. [rust-vmm/xen](https://github.com/rust-vmm/xen) содержит низкоуровневые Rust-интерфейсы, но не является готовым менеджером виртуальных машин.

## Архитектура MVP

Каждый управляющий хост предоставляет клиентский API и участвует в общем консенсусе с настроенным положительным целочисленным весом. Запрос клиента можно отправить на любую control-plane ноду; API не закреплён за одной нодой. Worker-хосты выполняют команды через локальный агент и не участвуют в кворуме. В MVP веса применяются только к кворуму; размещение нагрузок пока не входит в проект.

При добавлении control-plane сервера его положительный целочисленный вес задаётся API-запросом добавления. Вес не меняется автоматически из-за доступности или производительности сервера; для изменения требуется отдельный явный API-запрос. Для фиксированного состава кворум — это набор уникальных голосующих узлов, суммарный вес которых не меньше `floor(общий вес / 2) + 1`. Во время изменения конфигурации требуется кворум как по старым, так и по новым весам. Подробности и границы текущей реализации описаны в [`docs/consensus-model.md`](docs/consensus-model.md).

Начальная Rust-библиотека находится в `src/`. Реализованы команды изменения состава, расчёт статического взвешенного большинства, joint quorum, детерминированное применение записей перехода, трекер фиксации membership-записей, leaderless Paxos для последовательных слотов, SQLite-хранилище durable acceptor state с WAL и `synchronous=FULL`, чтение committed-журнала пачками, версионированное кодирование Paxos RPC и TCP request/reply транспорт с циклом обслуживания до сигнала остановки. Координатор локально выделяет слот и ballot, устойчиво сохраняет выбранное значение, повторяет вытесненные раунды и переносит запрос в следующий слот при конфликте. `CommittedLogApplier` передаёт opaque-команды прикладной state machine строго по порядку и устойчиво сохраняет applied cursor; обработчик должен быть идемпотентен по номеру слота. RPC обслуживаются последовательно; ошибка одного соединения останавливает текущий цикл. Конкретные команды VM, HTTP API, конкурентная обработка запросов, worker-агент и FFI к `libxl` остаются следующими этапами. Координатор требует сериализовать запросы на одном процессе; дедупликация клиентских повторов через operation ID пока не реализована.

## Разработка

Нужен Rust toolchain с Cargo. Из корня репозитория:

```sh
cargo fmt --check
cargo check
cargo test
```

## Изученные открытые проекты

- [XAPI](https://github.com/xapi-project/xen-api) и [xenopsd](https://github.com/xapi-project/xenopsd) — полноценный Xen-native стек управления и полезный образец разделения API/control plane и исполнения операций на хосте; в основном написаны на OCaml.
- [Xen Orchestra](https://github.com/vatesfr/xen-orchestra) — зрелый management backend с REST API, управлением VM и пулами; построен поверх XAPI, написан на JavaScript, лицензия AGPL-3.0.
- [rust-vmm/xen](https://github.com/rust-vmm/xen) — низкоуровневые Rust bindings и интерфейсы, не готовый backend.

Все перечисленные проекты имеют открытый исходный код. При заимствовании или форке нужно отдельно учитывать лицензии компонентов.

## JSON-конфигурация домена

JSON Schema находится в [`schema/xl-domain.schema.json`](schema/xl-domain.schema.json). Она сгруппирована по основным разделам официального [руководства `xl.cfg`](https://xenbits.xen.org/docs/unstable/man/xl.cfg.5.html): общие настройки, загрузка, устройства, PV/HVM/PVH, device model, графика и параметры архитектур ARM/x86. Имена опций сохранены; например, `memory` задаётся числом в MB, `cpus` — выражением CPU-list, а списки `xl.cfg` представлены JSON-массивами.

Покрыты распространённые параметры из всех основных разделов, но это пока не исчерпывающая копия всех опций и их версионных различий. Неописанные свойства отклоняются, поэтому перед использованием схемы с конкретной версией Xen нужно сверить её с соответствующим руководством. Межполевые ограничения, например `maxmem >= memory`, а также применимость опций к типу гостя и архитектуре должны дополнительно проверяться backend’ом.

Для устройств разрешены как исходные строки `xl.cfg`, так и JSON-объекты. Строки сохраняют совместимость с device mini-языками Xen; объекты удобнее для REST, но для них backend должен реализовать преобразование в структуры `libxl`. JSON Schema сама такого преобразователя не задаёт.
